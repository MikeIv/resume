# Цикл работы агента

Перед нетривиальной задачей — **класс** и **фаза**. Фазы не пропускать без согласия.

Класс определяет **агент**, не человек: для M+ он называется одной строкой в блоке «Понимание», чтобы человек мог поправить сразу. Если scope вырос — файлов или модулей больше, чем предполагалось, — переобъяви класс и переключись на процесс нового класса, а не продолжай молча.

| Класс  | Примеры           | Процесс                                     |
| ------ | ----------------- | ------------------------------------------- |
| **S**  | typo, rename      | Execute → Verify                            |
| **M**  | фича, 1–4 файла   | Discuss → Execute → Verify                  |
| **L**  | модуль, 5+ файлов | Discuss → Plan → Execute (волнами) → Verify |
| **XL** | миграция          | Полный цикл + `.planning/`                  |

**Фазы:** Discuss (`01`) → Plan (`02`, L+) → Execute (`03`) → Verify (`04`).

**Verify:** по `04` — S lint · M `pnpm lint:all` (+ `typecheck` при API) · L+ `pnpm verify` + `pnpm build`.

**Принципы:** минимальный diff · эталон из репо (`90`) · причина, не симптом (M+) · типы первыми (L+/API) · неуверенность → Discuss.

**Стоп:** противоречивые требования; auth/роли/контракт API; удаление данных; нет env/API; scope меняется — спросить.

**Язык:** русский. **Приоритет:** проектные правила > личные (Cursor User Rules / `~/.dsh/AGENTS.md`).

# Экономия токенов

Лимит — **проза в чате**, не глубина анализа, diff и проверок.

## Чат по классу

| Класс  | Ответ                                  |
| ------ | -------------------------------------- |
| **S**  | 2–4 предложения или bullets            |
| **M**  | ≤120 слов; fast-path `01` → «Понял: …» |
| **L+** | bullets по волне/Verify, без вводных   |

**Без лимита:** «подробно» / «объясни»; security; необратимые действия; блокеры.

## Контекст

- Один фокус — текущая волна; код — только релевантные файлы
- Новая сессия: `@.planning/PROJECT.md` + `state.md`; задача: `brief.md` / `plan.md`; детали — `05`
- **Новый чат на волну** — не тащить фиксы/коммит в ту же сессию, что вёрстка
- Не читать `01`–`06`, если они уже покрыты always-applied (`00`, `07`, `90`) и задача не L+
- Не glob `app/**/*` — только файлы из таблицы эталонов в `90` + целевой компонент/страница

## MCP и инструменты

Имена — инструменты Cursor (MCP); в DS Harness их заменяют серверы `context7` / `nuxt` / `mdn` и REST-хелпер Figma (`09-figma-rest`).

| Инструмент | Лимит |
| ---------- | ----- |
| **Figma `get_design_context`** | **1×** на волну — primary breakpoint (обычно mobile) |
| **Figma `get_screenshot`** | До 2× — tablet/desktop, если нужна сверка; не дублировать context |
| **Figma `get_metadata`** | Только для slug/имён страниц, не для вёрстки секции |
| **Browser MCP** | Только по явному запросу пользователя (`05`, `04`) |
| **`pnpm lint:all`** | **1×** перед «готово»; не перезапускать после каждой правки |
| **Широкий поиск** (Cursor: Task explore; DS Harness: `subagent`) | Не для точечного grep/read по известным путям |

Несколько node-id в промпте — не повод вызывать `get_design_context` на каждый; остальные — screenshot или адаптация по брейкпоинтам проекта.

## Качество — не сжимать

Типы, edge cases, Verify (`04`), security, минимальный diff (`03`/`06`), сверка с кадром Figma — полный объём.

# Маршрутизация инструментов

Исполнителей двое, процесс один: правила действуют в обоих инструментах.
Инструмент — это **исполнитель волны**, а не «место, где я работаю».

## Роли

- **Писатель** — один инструмент на волну: правит код, запускает свои проверки, закрывает волну.
- **Проверяющий** — **другой** инструмент: сообщает только факты (расхождения с brief, упавшие проверки, нарушения правил). **Сам не правит.**
- **Решающий** — человек: brief, план, коммит. Класс задачи определяет агент (`00`), человек корректирует его одним словом.

Находки вносит автор волны; проверяющий только докладывает.

## Кто на какой работе

| Работа | Инструмент |
| --- | --- |
| Микроправки, визуальная подгонка, LSP-переименования, правка «на глаз» | Cursor |
| Волны L/XL: много файлов, прогоны, ожидания, повторы | DS Harness |
| Механическая верификация: линты, сверка `git diff` с brief, поиск нарушений правил | DS Harness |
| Содержательное ревью: архитектура, риски, спорные места | Cursor либо DS Harness на усиленной модели |

**Класс M:** пишет **Cursor**, проверяет **DS Harness** фактами по `git diff` и brief — по завершении задачи, а не после каждой правки.
**Класс L/XL:** план через DS Harness, волны по 1–3 задачи, проверка **другим** инструментом после каждой волны.
**Класс S:** только Cursor — правка и линт, без `.planning/` и без аудита.

Эвристика: **печатаешь и смотришь глазами — Cursor; ждёшь и проверяешь — DS Harness; решаешь — человек.**

**Ограничение песочницы.** DS Harness сам запускает линты и `git`. Всё, что поднимает `esbuild` — тест-раннер, `build`, `dev` — и сетевые вызовы (Figma REST, MCP) требуют расширения доступа: их запускает автор, а невыполненную проверку указывают в отчёте.

## Передача: шина — `.planning/`

- `brief.md` — вход задачи M+ (`brief-template.md`); `plan.md` — план L/XL.
- `state.md` — выход каждой волны; строки **«Ручка у»** и **«Файлы волны»** обязательны.
- **У файла в единицу времени один писатель.** Арбитр — `git status` / `git diff`.

## Запрещено

- Двум инструментам править одни файлы одновременно.
- `build` пока жив `dev` — они дерутся за `.nuxt`. Пока dev запущен, проверки идут линтами, а тесты запускает автор.
- Править `AGENTS.md` руками: он генерируется из `.cursor/rules` командой `node .cursor/sync-rules.mjs`.
- Коммитить без явной просьбы (`03`).
- Аудит в режиме записи: аудит ведётся в сессии с правами **read-only**.

## Словарь инструментов

Имена Cursor в правилах (`Task explore`, `ReadLints`, команды `/brief` и др.) переводятся в `AGENTS.local.md`, раздел «Инструменты Cursor → DS Harness».

# Резюме-сайт (Nuxt 4, SSG)

**Пакет:** `resume-site` · **Nuxt 4.6** · **SSG** (`nuxt generate`) · цель — GitHub Pages
(`/resume/`), запасной вариант — Vercel.

**Назначение:** одно резюме для трёх аудиторий — человек (HR, тимлид), ATS
(одна колонка, текст), AI-агент (`llms.txt`, JSON Resume). Позиционирование —
Nuxt fullstack разработчик с современной агентской разработкой.

## Источник данных — только `data/resume.yaml`

- Единственный источник правды. Сайт, PDF, DOCX, `resume.json`, `resume.txt`,
  `llms.txt`, `og.png`, hh-пакет собираются из него; правка текста — там.
- Схема — `shared/schema/resume.ts` (zod). Новое поле сначала в схему, потом в YAML и
  в экспортёры.
- Факты только измеримые: коммиты, файлы, тесты, Lighthouse. Никаких выдуманных
  цифр и клиентов под NDA; в свободные тексты не попадают телефон и почта.

## Команды

```bash
pnpm dev | generate | verify | test | typecheck | lint:all
pnpm build:all     # hh-пакет, og.png, статика, PDF, DOCX, проверка PDF
pnpm audit:site    # Lighthouse с порогами 95/100/95/95
pnpm screenshot    # .preview/{desktop,mobile-*}.png
pnpm rules:sync    # .cursor/rules/*.mdc → AGENTS.md + .dsh/skills
```

## Правила артефактов

- PDF: одна колонка, без иконок и картинок, **обязательный текстовый слой**,
  не больше двух страниц. Проверка — `pnpm check:pdf`, её падение = красный билд.
- JSON Resume обязан соответствовать схеме, `meta.canonical` и
  `projects[].keywords` не удалять: на них опираются HR-боты.
- Статика с baseURL: внутренние ссылки на артефакты идут через base (`/resume/...`),
  абсолютный адрес — из `NUXT_PUBLIC_SITE_URL` (дефолт — GitHub Pages). Не хардкодить
  `/resume.json` в шаблонах — только через хелперы с base.
- Сгенерированные PDF/DOCX и `.preview/` в git не идут (см. `.gitignore`).

## Ограничения

- Не менять `srcDir`, SSG-режим, пороги Lighthouse и структуру `data/resume.yaml`
  без запроса.
- Секреты — только в `.env` (`NUXT_PUBLIC_*` — публичные значения). СНИЛС, паспорт
  и полную дату рождения не публиковать.
- Стили — CSS Modules + `$style`, SCSS с токенами; глобальные классы не заводить.
- Коммит — по слову «коммить», push — по «пушь». Сообщения коммитов — на английском
  (Conventional Commits), тело — тоже.
